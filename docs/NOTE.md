## 📋 Purpose
This document serves as a **single source of truth** for all contributors regarding:

1. **Which files are considered “system files.”**  
2. **When and how they may be modified.**  
3. **Consequences for unauthorized changes.**  

Treat this note as the first thing you read before touching any part of the repository.

---

## 🗂️ What Counts as a System File?
- Anything under the top‑level directories: `src/`, `config/`, `scripts/`, `docs/` that is marked with a `# SYSTEM` comment at the top of the file.  
- Files listed in `core`, etc. in `core`, etc. are system files by default.
 (auto‑generated by CI).  
- Files that contain the phrase **“DO NOT EDIT”** in their header comment block.

> **Tip:** Run `git grep -i "SYSTEM"` to locate all system‑file markers.

---

## ✅ When Editing Is Allowed
| Situation | Required Action |
|-----------|-----------------|
| **Explicit instruction from the previous employee** (e.g., a hand‑off email, ticket, or comment) | Add a comment at the top of the file: `# EDITED BY <your‑name> – <date> – Reason: <brief description>` |
| **Critical security patch** (e.g., CVE fix) | Open a PR with the label `security‑patch` and reference the ticket. The PR must be approved by at least one senior maintainer before merging. |
| **Automated migration** (e.g., `npm run migrate`) | Ensure the migration script is listed in `scripts/` and has a corresponding entry in `CHANGELOG.md`. No manual edits to system files are required. |

If none of the above apply, **do not edit** the file.

---

## 🚫 Prohibited Actions
- Directly committing changes to a system file without a documented instruction.  
- Removing or altering the `# SYSTEM` marker.  
- Bypassing the review process for security‑related changes.  

Violations will be logged by the CI pipeline and may trigger a rollback or disciplinary action.
